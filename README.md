# Лабораторная работа 1.6

Дисциплина «Технологии и методы программирования». Выполнены все 11 пунктов задания.
Решение использует стандартную библиотеку Java без фреймворков и сторонних зависимостей.

## Запуск

Нужна Java с модулем компилятора `jdk.compiler` (обычно JDK 17 или новее).

```bash
cd ~/trash/lab6
./run.sh 1
```

Первый аргумент — номер задания от 1 до 11. Скрипт компилирует два исходных файла
в `build`, затем запускает выбранный пример. Отдельная команда `javac` не требуется.

```bash
./run.sh 2       # бесконечные таймеры, остановка Ctrl+C
./run.sh 2 3     # те же таймеры, остановка через 3 секунды
./run.sh 3       # остановка общим флагом через 5 секунд
./run.sh 4       # остановка interrupt через 5 секунд
./run.sh 5       # намеренно ошибочный обмен без синхронизации
./run.sh 6       # ReentrantLock и Condition
./run.sh 7       # synchronized, wait, notifyAll
./run.sh 8       # π в пяти потоках; может потребовать десятки секунд
./run.sh 9       # семь философов
./run.sh 10      # пять писателей и десять читателей
./run.sh 11      # бесконечная модель душевой, остановка Ctrl+C
./run.sh 11 3    # модель душевой с корректным завершением через 3 секунды
```

Без ограничения времени пункты 2 и 11 работают бесконечно, как в задании.
Для проверки корректного освобождения душевой используйте запуск с ограничением:
главный поток прерывает посетителей и дожидается их завершения. Ctrl+C завершает JVM.
Пункты 5–7 передают по 1000 значений от каждого производителя, пункты 9–10
выполняют по пять циклов на участника. Это позволяет дождаться результата демонстрации.

## Реализация и пояснения

### 1 Создание потоков

`HelloThread` получает номер через конструктор. Сначала запускаются все десять
потоков, затем главный поток вызывает `join` для каждого. Последней строкой выводится
сообщение главного потока. Порядок приветствий не фиксирован.

### 2 Периодический вывод

Десять потоков вызывают `Thread.sleep(1000)` и выводят собственный номер и прошедшее
время. Время измеряется через `System.nanoTime`, отдельно от момента запуска каждого
потока. Интервал может быть больше секунды из-за планирования и вывода в консоль.

### 3 Остановка через разделяемую память

Главный поток через пять секунд устанавливает общий флаг `volatile`.
`volatile` обеспечивает видимость записи рабочим потокам. Проверка после `sleep`
исключает дополнительный вывод после обнаружения отмены. Сам сон не прерывается,
поэтому завершение может задержаться примерно на оставшуюся часть секунды.

### 4 Остановка через прерывание

Главный поток через пять секунд вызывает `interrupt` у всех десяти потоков.
Спящий поток получает `InterruptedException`, восстанавливает признак прерывания
и выходит. Главный поток дожидается завершения всех участников через `join`.

### 5 Производители и потребители без синхронизации

Десять производителей и десять потребителей используют кольцевой буфер на десять
элементов. Числа уникальны: производитель с индексом i создаёт значения
`i * 1000 + j`, где j от 0 до 999. В `UnsafeBuffer` нет блокировок, атомарных полей
или `volatile`. `Thread.yield` в ожидании не обеспечивает синхронизацию.

Возможные ошибки:

- Два производителя видят одно свободное место и перезаписывают данные друг друга.
- Два потребителя читают один элемент, появляются повторы и пропуски.
- Операции `count++`, `count--` и изменение индексов теряют обновления.
- Проверка заполненности и изменение буфера не атомарны; счётчик может выйти за границы.
- Нет гарантии видимости изменений между потоками; ожидание может не закончиться.

Сценарий: два производителя читают `count = 0`, каждый вычисляет новое значение 1.
После двух записей счётчик равен 1 вместо 2. Аналогичные гонки затрагивают индексы.
У Таненбаума дополнительно разобрана потеря пробуждения: сигнал приходит между
проверкой пустого буфера и фактическим переходом потребителя в сон.

Чтобы демонстрация ошибки не зависала навсегда, главный поток через две секунды
прерывает незавершённые операции. Прерывание служит только для остановки;
корректности доступа к буферу оно не обеспечивает. После `join` подсчитываются
пропуски и повторы. Каждый потребитель записывает статистику в собственный массив,
поэтому сама проверка результатов не добавляет гонку. Ошибка зависит от расписания
и не обязана проявляться при каждом запуске.

### 6 Буфер с ReentrantLock

Проверка условий, индексы, данные и счётчик защищены одной блокировкой.
Производители ждут на `notFull`, потребители — на `notEmpty`.
`await` освобождает блокировку на время ожидания и снова захватывает её перед возвратом.
После изменения состояния пробуждается участник соответствующей очереди.
Условия проверяются в `while`: после пробуждения состояние может уже измениться,
также возможны ложные пробуждения. Освобождение блокировки выполняется в `finally`.
Итог: 10000 полученных значений, без пропусков и повторов.

### 7 Буфер на мониторе объекта

Методы `put` и `take` помечены `synchronized`. `wait` временно освобождает монитор,
а `notifyAll` пробуждает ожидающих после изменения состояния. Здесь у производителей
и потребителей общая очередь ожидания: одиночный `notify` может разбудить поток,
который не способен продолжить работу. Поэтому используется `notifyAll` и проверка
условий в `while`. Результат обмена такой же, как в пункте 6.

### 8 Вычисление числа π

Формула Лейбница:

```text
π = 4 * Σ (-1)^n / (2n + 1), n = 0, 1, ...
```

После N членов оценка остатка знакопеременного ряда равна `4 / (2N + 1)`.
Для N = 4000000000 она меньше `5 * 10^-10`, что даёт запас относительно
требуемой абсолютной погрешности `10^-9`.

Ровно пять потоков делят два миллиарда соседних пар членов на равные непрерывные
участки. Пара вычисляется как `2 / ((4k + 1) * (4k + 3))`, что алгебраически равно
`1/(4k+1) - 1/(4k+3)`. Знаменатель вычисляется в `double`, без переполнения `long`.
Используется суммирование Кэхэна для снижения накопления ошибок округления.
После `join` главный поток суммирует пять результатов и умножает их на четыре.
`Math.PI` используется только для проверки, а не для получения результата.
Оценка остатка относится к математическому ряду; фактическая погрешность вычисления
с плавающей точкой также проверяется программой. Прямой ряд сходится медленно,
поэтому этот пункт существенно тяжелее остальных.

### 9 Обедающие философы

Семь философов используют семь вилок, каждая представлена `ReentrantLock(true)`.
Для еды нужны обе соседние вилки. Если все сначала возьмут левую вилку,
может возникнуть циклическое ожидание и взаимная блокировка.
В решении каждый философ сначала берёт вилку с меньшим номером, затем с большим.
Единый порядок исключает цикл ожидания. Вилки освобождаются во вложенных `finally`,
в том числе при прерывании. Справедливые блокировки уменьшают риск голодания;
время ожидания всё равно зависит от планировщика. Каждый философ ест пять раз.

### 10 Читатели и писатели

Общее целое число защищает справедливый `ReentrantReadWriteLock(true)`.
Десять читателей могут держать read lock одновременно; пять писателей берут
исключительную write lock. Во время записи нет других писателей и читателей.
Сон внутри секции чтения моделирует длительную обработку, поэтому чтения могут
перекрываться, хотя отдельные строки консольного вывода печатаются последовательно.

При неограниченном допуске новых читателей писатель может голодать — этот случай
описан в учебнике. Справедливый режим учитывает очередь ожидающих участников;
в коде не применяется обходящая очередь операция `tryLock`.
Каждый писатель делает пять увеличений, итоговое значение — 25.

### 11 Душевая

Класс `ShowerRoom` предоставляет четыре требуемых публичных метода:
`womanWantsToEnter`, `manWantsToEnter`, `womanLeaves`, `manLeaves`.
Состояние комнаты и очередь заявок защищены `ReentrantLock`.
Ожидание выполняется через `Condition.await`, пробуждение — через `signalAll`.

Вход разрешён, если посетитель стоит первым в очереди, есть свободное место
и комната пуста либо занята посетителями того же пола. Таким образом,
одновременно внутри не более десяти человек и только одного пола.
Индикатор принимает значения `EMPTY`, `WOMAN`, `MAN`; последний выходящий
переводит его в `EMPTY`.

Очередь нужна, чтобы постоянный приход посетителей одного пола не отодвигал
ожидающих другого пола бесконечно. Когда первым становится посетитель другого
пола, комната постепенно освобождается. Это может снизить заполненность,
но обеспечивает порядок допуска. При прерывании ожидающего его заявка удаляется
и остальные пробуждаются. При прерывании моющегося выход выполняется в `finally`.
Методы выхода предполагают парное использование после успешного входа.

Модель запускает 20 мужчин и 20 женщин. Каждый в бесконечном цикле занимается
своими делами, входит, моется и выходит. Мытьё происходит вне блокировки,
так что посетители действительно могут пользоваться комнатой одновременно.
Строки журнала содержат имя потока, действие, число людей и состояние индикатора.

## Проверка

```bash
./run.sh 1
python3 check.py
```

Python 3 нужен только для проверочного скрипта. Он запускает все 11 упражнений,
проверяет таймеры и завершение, трижды проверяет каждый корректный буфер на
пропуски и повторы, сравнивает π с требуемой точностью, считает приёмы пищи
и записи. По журналу душевой восстанавливает находящихся внутри посетителей
и проверяет вместимость, отсутствие смешения полов, участие всех 40 потоков
и освобождение комнаты при отмене. Прогоны не являются доказательством
корректности всех возможных расписаний; необходимые инварианты объяснены выше.
